# 性能优化实验记录

> 时间：2026-11-21
> 环境：Windows + WSL2 / MySQL 8.0.42 / Redis 5.0.7 / RabbitMQ 3.8 / Node 24 单进程
> 工具：`scripts/loadtest.js`（自写，纯 Node），并发 20~50，每轮 10 秒

---

## 一、牌面接口 `GET /api/cards`

改造前 670 QPS，第一反应是「每个请求都过一次 Redis 限流」。

实测发现两件事：
1. 这个接口的数据启动时就加载在内存里，**没有数据库、没有缓存未命中**
2. 每次请求都在做 `JSON.stringify(78 张牌 + fullDeck)`，然后才发出去

### 改动与结果

| 版本 | 改动 | QPS | P99 |
|---|---|---|---|
| 基线 | — | 669.6 | 145 ms |
| ① | 响应体启动时序列化一次（`CARDS_BODY` 常量 + ETag + Cache-Control） | **967.0** | 72 ms |
| ② | 静态只读接口跳过 Redis 限流，只留进程内限流兜底 | **1019.2** | 70 ms |

**结论**：这个接口的瓶颈是「重复序列化」而不是「Redis 限流」。
Redis 那一步省掉只多赚了 5%，真正的大头是 `JSON.stringify`。

> 顺带说明：Redis 限流对静态接口是纯成本——一次网络往返换一次计数，
> 而它保护的东西（数据库、模型调用）根本不在这个接口里。
> 所以现在分工是：**静态接口走进程内限流，有成本的接口（登录/兑换/起卦）走 Redis 精确限流。**

## 二、提交接口 `POST /api/reading/async`

这个接口一次请求要：幂等 INSERT → 开事务 → 扣额度 UPDATE → SELECT 余额 → 插任务 → 插流水 → 提交 → 发消息。

### 2.1 先验证「是不是连接池太小」

| 配置 | QPS | P99 |
|---|---|---|
| 池 5，单用户 | 80.1 | 385 ms |
| 池 20，单用户 | 81.9 | 357 ms |

**没有变化** → 瓶颈不在连接数。

### 2.2 真正原因一：热点行锁

所有压测请求扣的是**同一个用户**的同一行额度。
InnoDB 对该行加排他锁，事务串行执行，吞吐上限 ≈ 1 / 单事务耗时。

换成 50 个用户（分散到 50 行）：

| 配置 | QPS | P99 |
|---|---|---|
| 池 5，50 用户 | 70.5 ~ 140.8（波动大） | 605 ms |
| 池 20，50 用户 | **311.2** | 108 ms |

### 2.3 真正原因二：worker 和 web 抢同一个连接池

50 用户、池 5 时只有 70 QPS，比单用户还慢——因为 worker 也在用同一个池（默认 5 条），
消费者每处理一条任务要 3 次写库（UPDATE 状态 → INSERT 解读 → UPDATE 完成），
把连接全占住，提交接口只能排队。

把池调到 20：**70.5 → 311.2 QPS，P99 605ms → 108ms**。

**结论**：worker 应该用独立连接池（独立进程 + 独立 `MYSQL_POOL_SIZE`），
或者干脆不跟 web 共享数据库连接额度。

### 2.4 附带发现：队列积压会拖慢生产端

压测时如果 worker 不在跑（或跑不过来），队列会快速堆积：

```
一轮 50 用户压测 → reading_tasks 积压 9355 条
下一轮同样配置    → 50 用户 QPS 从 318 掉到 140
```

消费能力是硬约束：mock 模式一次生成 300ms，prefetch=1，理论每秒 3.3 条，
而生产端能到 300+/s。**队列本来就是用来吸收这个落差的**，
但需要监控积压长度，并按积压水平横向扩 worker。

## 四、评估过但没做的优化

### 4.1 Redis 预扣额度，提交接口不碰 MySQL（秒杀模式）

**为什么没做**：额度对应钱。

秒杀敢用「Redis 预扣 + 异步落库」，是因为超卖一件商品可以退款了事；
额度扣错是资损，而且这个项目没有对账系统兜底。改成 Redis 为准会带来：

- Redis 扣了、消息丢了 → 用户被扣但没生成解读，只能靠人工查
- Redis 丢数据（未持久化/主从切换）→ 余额凭空恢复，用户白嫖
- 所有读额度的地方（鉴权中间件、兑换码、后台）都要改读 Redis，一致性面变大

**如果真要做**，正确的顺序是：先做「事件表 + 对账任务」（每笔扣减落一条不可变事件，
定时比对 Redis 与 MySQL 的差额），再切读路径。这是周级工作量，不是加个脚本。

### 4.2 额度分片（一个用户拆多行，随机扣一行）

能解决 4.1 里的单用户热点，但代价是：

- `authGuard`、兑换码、后台改额度、注册送额度全部要改成 `SUM(shards)`
- 事务边界变复杂（一次扣减可能跨多行）
- 60 个用户的量级上，这是用正确性换一个用不上的吞吐

**什么情况下值得**：单用户极高频率扣减（比如会员权益批量核销）。

### 4.3 已做的轻量优化

- 提交路径用 `insertId` 代替「INSERT + SELECT id」，少一次往返
- 静态接口响应体预序列化 + ETag（支持 304）

## 五、下一步该做什么（如果继续）

1. **worker 独立连接池**，并按队列积压自动扩缩（现在要手动配 `MYSQL_POOL_SIZE`）
2. **队列积压监控**：`/api/health` 里加 `reading.jobs` 的消息数
3. **读写分离**：读接口（历史列表、详情）走只读库
4. 压测换成独立机器（现在客户端和服务端同机，绝对数字不可信，只看相对差异）
